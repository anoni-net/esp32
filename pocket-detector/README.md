# 隨身偵測器（pocket-detector）

不會寫程式的話，用電腦的 Chrome 或 Edge 到 [anoni.net/esp32/install/](https://anoni.net/esp32/install/) 接上板子按一下就能安裝，連上板子的方式見[連上板子](https://anoni.net/esp32/connect/)。這份說明寫給要看原始碼、自己建置或研究功能細節的人。

用 ESP32-S3 被動掃描周圍的 BLE 廣播，找出一直跟著你的 AirTag、SmartTag、Tile 與 Google 尋找我的裝置網路的追蹤器。同一份韌體也能檢查旅館房間裡的攝影機與無線裝置（房間檢查），以及閉門會議裡還開著藍牙或 Wi-Fi 的裝置（會議室檢查）。目標是做成反跟蹤工作坊的材料：參加者當場燒錄，帶回家就能用，之後再搭配文件站的指南。目前是原型，識別規則還需要實測。

研究用的模式（統計模式、Wi-Fi 基地台掃描、人流計數、flash 記錄）預設關閉，用途與記錄的內容見「研究用的模式」與「隱私設計」。

## 硬體

| 項目 | 說明 |
|---|---|
| 開發板 | ESP32-S3 N16R8（16 MB flash、8 MB PSRAM），雙 Type-C 的 44 腳 DevKitC 相容板 |
| GPIO 擴展板 | 開發板直接插上去，接蜂鳴器與 OLED 時不必用麵包板 |
| 蜂鳴器（選用） | 有源蜂鳴器，高電位觸發。低電位觸發的模組把程式裡的 `BUZZER_ON` 改成 `LOW` |
| OLED（選用） | 0.96 吋 SSD1306，I2C 介面，128×64 |
| 杜邦線 | 母對母，蜂鳴器用 3P，OLED 用 4P |

只有開發板也能執行，板上的 RGB LED 會顯示狀態，詳細資訊從序列埠輸出。蜂鳴器與 OLED 沒接也不影響運作，OLED 在開機時偵測，偵測不到就略過。

### 接線

接線一律在拔掉 USB 線、斷電時進行。擴展板每支 GPIO 有一排三根針，絲印 `G`、`V`、`S`，分別是接地、電源、訊號。

| 零件 | 零件的腳 | 接到 |
|---|---|---|
| 蜂鳴器 | `S` | GPIO4 那排的 `S` |
| | `+` | GPIO4 那排的 `V` |
| | `-` | GPIO4 那排的 `G` |
| OLED | `GND` | 任一個 `G` |
| | `VCC` | 3.3V |
| | `SCL` | GPIO9 那排的 `S` |
| | `SDA` | GPIO8 那排的 `S` |

- OLED 的 `VCC` 接 3.3V。模組的 I2C 上拉電阻接在自己的電源，接 5V 時 SDA 與 SCL 也會是 5V，ESP32-S3 的腳位不耐 5V。擴展板若有 3.3V 與 5V 的切換跳帽，先確認位置
- 0.96 吋 OLED 的腳序有 `GND VCC SCL SDA` 與 `VCC GND SCL SDA` 兩種，接反會燒壞模組，照模組上的絲印接
- OLED 背面的 `IIC ADRESS SELECT` 決定位址是 `0x3C` 或 `0x3D`，程式兩個都會試，偵測結果印在序列埠
- 蜂鳴器開機時短響一聲，可以用來確認接線

選腳位時避開以下幾支：

| 腳位 | 用途 |
|---|---|
| GPIO0、3、45、46 | 開機模式的 strapping pin |
| GPIO19、20 | USB |
| GPIO35 到 37 | N16R8 的 PSRAM |
| GPIO43、44 | `COM` 孔的序列埠 |
| GPIO48（部分板子是 38） | 板上的 RGB LED |

## 燒錄

### Arduino IDE

1. 開發板管理員安裝 `esp32`（Espressif Systems），程式庫管理員安裝 `NimBLE-Arduino` 2.x 與 `U8g2`（olikraus）。沒接 OLED 也要安裝 `U8g2`，否則無法編譯
2. 把 repo 根目錄 `lib/` 底下的 `netupdate`、`phonelink` 兩個資料夾複製到 Arduino 的 `libraries` 資料夾（macOS 在 `~/Documents/Arduino/libraries/`），這是幾個工具共用的元件
3. 開啟 `pocket_detector/pocket_detector.ino`，同一個資料夾的 `types.h` 會一起開成分頁
4. 開發板選 `ESP32S3 Dev Module`，設定如下表
5. USB 線接開發板標 `COM` 的那個孔，選對序列埠後上傳
6. 開啟序列埠監控視窗，鮑率 115200

| 設定 | 值 |
|---|---|
| Flash Size | 16MB (128Mb) |
| PSRAM | OPI PSRAM |
| Partition Scheme | 16M Flash (3MB APP/9.9MB FATFS)，flash 記錄要用到其中的 FAT 分割區 |
| USB CDC On Boot | Disabled |

上傳失敗時，按住 BOOT 鍵、按一下 RST 鍵、放開 BOOT 鍵，讓板子進入下載模式再試一次。

板子沒有電源開關，拔掉 USB 線就是關機。紀錄只在記憶體裡，隨時斷電都不會損壞，只有上傳程式的途中不要拔線。

以 esp32 3.3.12、NimBLE-Arduino 2.x、U8g2 在 N16R8 板上實測過燒錄、蜂鳴器與 OLED。

### 發布韌體到 assets.anoni.net

韌體分成兩個發布通道，網址都寫死在程式裡：

| 通道 | 網址 | 內容 |
|---|---|---|
| 正式 | `https://assets.anoni.net/esp32-tracker/` | 實機測試通過的版本，板子預設讀這裡 |
| 測試 | `https://assets.anoni.net/esp32-tracker-test/` | 每次修改都發布，給開發用的板子 |

`tools/publish_firmware.sh` 建置韌體，從 `firmware.bin` 找出建置時間，計算 SHA-256，把 `tracker-<SHA-256 前 12 碼>.bin` 與 `latest.json` 上傳到發布主機的 `esp32-tracker-test/`，最後經過 Cloudflare 下載一次比對內容。它只發布到測試通道，在 repo 根目錄執行 `./tools/publish_firmware.sh pocket-detector`，發布主機由 `PUBLISH_HOST`、`PUBLISH_ROOT` 指定（或寫在不進版控的 `tools/publish.local.env`），設定在 `publish.env`。有還沒 commit 的變更時拒絕發布，`latest.json` 的 `commit` 欄位對得回原始碼。`--dry-run` 只建置並印出 `latest.json`。

開發用的板子在面板打開「接收測試版」並短按 BOOT 確認（或序列埠送 `channel test`），從測試通道更新到剛發布的版本，再用 `tests/hil/run_hil.py` 做實機測試（見下方「測試」）。通過的話執行 `./tools/promote_firmware.sh pocket-detector`，在發布主機上把測試通道的韌體檔與 `latest.json` 原封不動複製到正式通道，不重新建置，正式版的建置時間與 SHA-256 跟測過的檔案完全相同。實機測試的紀錄比對的是板子開機時印出的建置時間，用 USB 燒進去的版本建置時間不同，不能拿來推正式版。緊急修正可以加 `--force` 略過。

2026-11-27 以前的韌體沒有測試通道，只讀正式通道。搬到 `anoni-net/esp32` 之前發布的版本（例如正式通道的 `616609b`）是在社群工作區建置的，`latest.json` 裡的 commit 在這裡查不到。從新 repo 第一次發布之後，版本才對得回原始碼。

板子比對的是建置時間，所以同一份原始碼重新發布也會被當成新版。只往新的版本更新：用 USB 燒進比 assets 上還新的版本之後，按「檢查並安裝新版」會顯示「assets.anoni.net 上的版本比目前的舊」，不會換回舊版（2026-11-26 B 板曾因此被換回早上發布的版本）。韌體的檔名帶雜湊，內容不會變，Cloudflare 快取舊檔也沒關係。`latest.json` 由板子加上隨機的查詢字串讀取，避開快取。

### 面板網頁

手機面板的網頁在 `pocket_detector/panel.html`。建置前 `tools/make_panel.py` 用 gzip 壓縮成 `panel_gz.h`（約 72 KB 變 26 KB），板子送出時標上 `Content-Encoding: gzip`，瀏覽器自己解壓縮，板子直接從 flash 送出，不多用記憶體。用板子的熱點第一次打開面板快很多，iPhone 自動跳出面板時尤其明顯。

PlatformIO 建置時會自動重新產生（`platformio.ini` 的 `extra_scripts`），`panel_gz.h` 也放進版控，用 Arduino IDE 編譯時不必先執行腳本，但改了 `panel.html` 之後要執行 `python3 -I tools/make_panel.py`。`tools/run_tests.sh` 會檢查兩者是否一致（比對 `panel.html` 的 SHA-256，並把 `panel_gz.h` 解壓縮回來比對內容）。

### 多語系

韌體有正體中文、簡體中文與英文三個版本，分開建置、分開發布。原文是正體中文，寫在 `panel.html` 與原始碼裡，翻譯放在 `i18n/`：

| 檔案 | 內容 |
|---|---|
| `i18n/panel.toml` | 面板網頁裡含中文的片段，以 HTML 標籤、引號與 `\n` 切開 |
| `i18n/firmware.toml` | 韌體裡用 `TR("…")` 包起來的字串：面板上的提示、裝置的類型、房間檢查的理由、網址更新的訊息、藍牙文字通道的回覆 |
| `i18n/trad_chars.txt` | 原文用到的正體字，檢查簡體中文的翻譯時不能出現 |

| 語系 | PlatformIO 環境 | 建置旗標 | 發布通道 |
|---|---|---|---|
| 正體中文 | `esp32-s3-n16r8` | 無 | `esp32-tracker/` |
| 簡體中文 | `esp32-s3-n16r8-zh-cn` | `-DFW_LANG_ZH_CN` | `esp32-tracker-zh-cn/` |
| 英文 | `esp32-s3-n16r8-en` | `-DFW_LANG_EN` | `esp32-tracker-en/` |

建置前 `tools/make_i18n.py` 從 `i18n/firmware.toml` 產生 `i18n_zh_cn.h`、`i18n_en.h`，`tools/make_panel.py` 產生 `panel_gz_zh_cn.h`、`panel_gz_en.h`，都放進版控。`TR("正體中文")` 在編譯期查表換成翻譯（`pocket_detector/i18n.h`），表裡沒有的字串編譯就失敗，不會默默留下原文。用 Arduino IDE 編譯時沒有旗標，就是正體中文版。

各語系的網址更新讀自己的通道，英文版的板子不會更新成正體中文版。要換語系，用網頁安裝或 USB 燒錄另一個語系的韌體，設定與記錄都會保留。發布與推正式版時加上 `--lang`：

```bash
./tools/publish_firmware.sh pocket-detector --lang en     # 設定在 publish.en.env
./tools/promote_firmware.sh pocket-detector --lang en
```

改了面板或原始碼的文字之後：

1. 要顯示給使用者的新字串用 `TR("…")` 包起來。序列埠的輸出只給開發者看，實機測試也比對它的文字，維持正體中文，不包 `TR`
2. 執行 `uv run --with opencc-python-reimplemented tools/make_i18n.py --extract`，新的字串加進目錄，簡體中文先用 OpenCC 轉一份草稿
3. 補上英文，校對簡體中文的用詞（固件、网络、设置、默认、热点……）
4. 執行 `./tools/run_tests.sh`，`make_i18n.py --check` 檢查翻譯齊全、printf 的格式一致，`tests/panel/test_i18n.py` 用每個情境載入翻譯過的面板，確認沒有 JS 錯誤

字串由片段組成時（例如 `TR("訊號很弱（") + rssi + TR(" dBm）…")`），翻譯照原文的順序接回去，英文需要的空白寫在翻譯裡。面板與韌體之間不比對文字：模式、房間檢查是否開始、版本比目前的舊，都用欄位或 HTTP 狀態碼判斷。OLED 只能顯示英數字，三個語系都是英文。專案網頁 anoni.net/esp32/ 與網頁上的模擬面板只有正體中文。

### 無障礙

面板照 WCAG 2.2 AA 檢查過（2026-11-27），三項修正：

- 開關與分段按鈕用 `aria-labelledby` 接到同一列的標題，輸入框有 `aria-label`，螢幕閱讀器念得出每個元件在設定什麼。尋找畫面打開時焦點移到「結束尋找」，後面的頁面設成 `inert`，關閉後焦點回到原處。頁面底部有捲動保留空間，聚焦的元件不會被固定的分頁擋住
- 文字對比至少 4.5:1，開關、輸入框外框、焦點外框至少 3:1，淺色與深色模式都算過（`tests/panel/test_contrast.py`）
- 狀態改成警示時用 `role=alert` 立刻讀出，其他狀態改變、自己按下的更新進度與上傳結果用 `aria-live` 讀出。剛打開面板時只讀警示，尋找畫面每秒變化的訊號數字不讀出

觸控目標都至少 24×24 px，320 px 寬時不必左右捲動，加大行距與字距後文字不會被切掉，這些在檢查時量過。頂端的倒數是一個按鈕，按一下暫停倒數、進度條與掃過的光，再按一次繼續，選擇記在手機上（2.2.2）。歷史的時間軸在觸發警示的追蹤器名稱前標「警示」，不只靠紅色（1.4.1）。底部分頁照分頁的模式實作：左右方向鍵切換、Home 與 End 到頭尾，只有目前的分頁在 Tab 的順序裡。還沒有用 VoiceOver、TalkBack 實際操作過。

### 測試

| 層級 | 指令 | 需要 | 測什麼 |
|---|---|---|---|
| 單元測試 | `tests/unit/run.sh` | C++ 編譯器 | 網址更新的版本判斷（`lib/netupdate/updcheck.h`，韌體編譯的是同一份）：建置時間比大小、`latest.json` 的格式檢查、不換回舊版 |
| 面板測試 | `python3 -I tests/panel/test_panel.py` | Chrome、Chromium、Brave 或 Edge | 在無頭瀏覽器載入面板、餵虛構的狀態，檢查 iOS 放大、提示擋住按鈕、重複的 id 與標籤、自動更新與韌體更新的各種狀態 |
| 實機測試 | `tests/hil/run_hil.py --port 埠` | 接在電腦上的板子 | 開機、狀態 JSON、OLED 畫面輸出、打記號、假追蹤器、重新開機後保留歷史。`--update` 先改接收測試版並從網路更新，換上的新版再檢查一次測試通道，接著照自動更新的條件檢查一次。`--long` 加上房間檢查、假警示與 OTA 自我測試 |
| 對比測試 | `python3 -I tests/panel/test_contrast.py` | 不需要 | 從 `panel.html` 讀出淺色與深色模式的顏色設定，計算文字、開關、輸入框外框、焦點外框的對比（WCAG 2.2 AA） |
| 人工檢查 | [tests/CHECKLIST.md](tests/CHECKLIST.md) | 板子與手機 | 按鍵、燈號、蜂鳴器、OLED、iPhone 與 Android |

`tools/run_tests.sh` 執行單元測試、面板測試與對比測試，加上 `--hil 埠` 時接著做實機測試。每次修改後至少執行前兩層，推正式版之前四層都要做。

實機測試要指定序列埠，打開序列埠會讓板子重新開機，正在記錄的板子不要拿來測。它不恢復原廠設定、不刪記錄，改過的門檻會改回去，但打的記號（`HIL-` 開頭）與假追蹤器（`fa:ke:00:00:00:01`）會留在板子的警示歷史與 flash 記錄。序列埠的完整輸出寫在 `tests/hil/results/`，裡面有附近裝置的位址，已經排除在版控之外。全部沒有失敗時，板子開機印出的建置時間寫進 `tests/hil/results/passed.tsv`。`tools/promote_firmware.sh` 只推這裡有、而且用 `--update` 從測試通道裝上並通過的版本：新版自己的網址更新也要讀得到測試通道，正式通道上的更新程式壞掉就沒辦法再從網址修好。自動更新被延後（有警示、手機連著熱點）或附近沒有 Wi-Fi 時記成略過。

`tests/hil/fake_board.py` 開一個假的序列埠，照韌體的格式回應指令，不接板子也能檢查實機測試腳本本身（`--reset-cmd __reset`，加上 `BROKEN=history` 這類環境變數可以讓某一項故意回錯）。模擬的結果不會寫進 `passed.tsv`。

## 運作方式

每 30 秒做一次 5 秒的被動掃描，只留下符合追蹤器特徵的廣播：

| 類型 | 識別方式 |
|---|---|
| Apple Find My | 廠商資料 `4C 00 12 19`，代表配件與主人分開。主人在附近時是 `4C 00 12 02`，不列入。接下來的狀態 byte，位元 4、5 是裝置類型：1 AirTag、2 相容的 Find My 配件、3 AirPods，0 是 Apple 自家裝置（見下方） |
| Samsung SmartTag | Service Data UUID `0xFD5A` |
| Tile | Service UUID `0xFEED`，或 Service Data UUID `0xFEED`、`0xFEEC` |
| Google 尋找我的裝置 | Service Data UUID `0xFEAA`，frame type `0x40` 或 `0x41` |
| Chipolo | Service Data UUID `0xFE33` |
| Pebblebee | Service UUID `0xFA25` |
| DULT | Service Data UUID `0xFCB2`，第 2 個 byte 的最低位元是 0（與主人分開）。是 1 代表主人在附近，不列入 |

狀態 byte 的類型是 0 的，是與主人分開的 Apple 自家裝置（iPhone、iPad、Mac 離線時也會發送 Find My 廣播），依據 PETS 2023 的論文 [Track You: A Deep Dive into Safety Alerts for Apple AirTags](https://petsymposium.org/popets/2023/popets-2023-0102.pdf) 表 4，iOS 不會對這類裝置發出安全警示。2026-11-25 一整天的實測，Apple 的「與主人分開」裝置有 361 個是這一類，AirTag 只有 10 個，快速測試門檻的 128 個警示裡有 114 個來自它們。這類裝置列為「Apple 自家裝置」，面板的清單不列出（只顯示數量），沒有打開 Wi-Fi 移動判斷時不警示，打開後確認一直跟著你經過好幾個地點才警示。同一篇論文也指出，把狀態 byte 改成 `0x00` 就能讓 iPhone 不警示，所以這類裝置不直接忽略，移動判斷仍能抓到偽裝的追蹤器。

DULT（Detecting Unwanted Location Trackers）是 Apple 與 Google 在 IETF 提出的防止不當追蹤規格，依據 [draft-ietf-dult-accessory-protocol-01](https://datatracker.ietf.org/doc/draft-ietf-dult-accessory-protocol/)（2026-10-27）。Service Data 的第 1 個 byte 是尋找網路的編號，現行草案移除了各家編號的登錄表，所以目前只記錄、不轉成品牌名稱。支援 DULT 的追蹤器會輪流發送自家格式與 DULT 格式的廣播，一次掃描裡 NimBLE 對同一個位址只留下最後一則，所以掃描的回呼逐筆檢查每一則廣播，記下每個位址最近的 DULT 狀態（保留 15 分鐘）：

- DULT 標示主人在附近：同一個位址的自家格式廣播也不列入。SmartTag、Tile、Chipolo、Pebblebee 自家的廣播不標示是否與主人分開，有了 DULT 才能排除主人自己帶著的追蹤器（Apple 自家格式已經標示與主人分開時，以 Apple 的為準）
- DULT 標示與主人分開、自家格式認不出來：列為「DULT 追蹤器」

有收到 DULT 廣播的掃描，記錄裡多一行 `DULT,掃描次數,與主人分開的,因為主人在附近而略過的`。

同一個位址同時符合三個條件，就判定為一直跟著你，序列埠輸出警示、LED 轉紅、蜂鳴器響三聲，按 BOOT 鍵確認後警示燈熄滅。30 分鐘沒再出現的紀錄會移除。

| 條件 | 預設值 | 排除的情況 |
|---|---|---|
| 首次與最後一次出現相隔 | 10 分鐘以上 | 短暫經過的追蹤器 |
| 訊號達到 -85 dBm 的掃描次數 | 6 次以上 | 隔牆或在路口的追蹤器。放在身上的通常在 -40 到 -70 dBm |
| 從第一次出現起，看得到它的掃描比例 | 70% 以上 | 時有時無、在附近來回的追蹤器 |

後兩個條件來自第一次實測：在住宅區，快速測試模式在 4 分鐘內被一個與主人分開的 Find My 配件觸發警示。它的訊號只有 -101 dBm，約 8 次掃描裡只出現 3 次，不在偵測者身上。

`QUICK_TEST` 設成 `true` 時門檻降為 2 分鐘、3 次掃描，拿身邊的追蹤器測試警示流程時使用。

| LED 燈號 | 狀態 |
|---|---|
| 藍燈恆亮 | 掃描中。掃描在背景進行，按鍵照常有反應 |
| 綠燈恆亮 | 附近沒有追蹤器 |
| 黃燈慢慢呼吸 | 附近有追蹤器，還沒達到警示門檻 |
| 紅燈快閃三下、停一下，重複 | 有未確認的警示，節奏跟蜂鳴器的三聲對應 |
| 白燈閃一下 | 沒有警示時按了 BOOT 鍵，在記錄裡打了一個記號 |
| 白燈慢慢呼吸 | 房間檢查中，短按 BOOT 取消 |
| 綠燈連閃兩下、停一下，持續 2 分鐘 | 房間檢查完成，連回熱點看報告。短按 BOOT 停止閃爍 |
| 白燈閃爍，越近閃得越快 | 尋找中，跟嗶聲同步。不用青色，避免跟 Wi-Fi 開著的燈號混淆 |
| 藍燈慢慢呼吸（尋找中） | 尋找的追蹤器 8 秒以上沒收到，可能換了位址或離開範圍 |
| 紅燈閃兩下、一聲短嗶 | 雙擊 BOOT 時附近沒有可以找的追蹤器 |

沒接蜂鳴器也能從燈號看出狀態。需要安靜、不想讓旁人察覺時，把 `BUZZER_ENABLED` 設成 `false`，只用燈號提示。

OLED 依板子正在做的事切換畫面，不必另外操作。螢幕的字型只有英文，畫面上用英文縮寫與數字：

| 情境 | 畫面 |
|---|---|
| 平常 | 大字的狀態（`CLEAR`、`WATCH`、`ALERT`、`ACKED`），右上角是追蹤器數量與掃描次數，掃描中多一個小方塊。下方依警示、訊號強度列出最多 3 個追蹤器，每列是類型、位址末四碼、訊號，以及一條離警示的進度條（跟手機面板相同，取各條件裡最低的）。警示時狀態列反白。打記號時右下角顯示 `MARK 3` 兩秒 |
| 尋找 | 大字的訊號強度（dBm）與長條，右上角是尋找剩下的時間。8 秒以上沒收到時長條只剩外框，顯示 `LOST?` 與多久前收到 |
| 剛打開 Wi-Fi 熱點 | 60 秒的 QR code，手機相機掃描就能加入熱點，旁邊是熱點名稱、網址，藍牙開著時加上配對碼。名稱加密碼太長、第 3 版 QR code 放不下時只顯示文字。QR code 含熱點密碼，有未確認的警示時改回平常的畫面 |
| 房間檢查 | 檢查中是目前的階段、進度條與剩下的秒數，完成後 2 分鐘顯示建議找出來與可以留意的數量 |
| 發聲 | 連線中，結果顯示 8 秒（`SOUND SENT`、`NOT FOUND`、`REFUSED` 等） |
| 韌體更新 | 等待按 BOOT 的倒數，或下載的進度 |
| 統計模式、人流計數 | 原本的統計表 |

同時符合好幾種情境時，依韌體更新、發聲中、房間檢查、尋找、熱點 QR code、發聲結果、房間檢查完成、平常的順序挑一個。畫面每 0.2 秒檢查一次，內容有變才重畫。程式在 `screen.h`，每個畫面只依傳進來的資料繪製。

沒接 OLED 的板子可以從序列埠檢查畫面：`oled dump` 把目前的畫面緩衝區印成十六進位，`oled demo find` 這類指令用假資料畫指定的畫面（接著 OLED 時在螢幕上停留 5 秒），把序列埠的輸出存成檔案，再用 `tools/oled_to_png.py` 轉成圖片。熱點的 QR code 畫面含有密碼，只印在序列埠，不寫進 flash 記錄。

門檻與掃描間隔都寫在程式開頭的設定區，可以依實測調整。

## 研究用的模式

偵測跟蹤者身上的手機、手錶、耳機，需要先知道周圍裝置的藍牙位址多久更換一次。以下的開關（`STATS_MODE`、`WIFI_SCAN`、`CROWD_MODE`、`LOG_TO_FLASH`）預設都關閉，研究時才打開。

### 統計模式（`STATS_MODE`）

記錄周圍所有藍牙裝置的完整位址，依類型統計：公開位址、隨機固定位址、可解析的隨機位址（RPA）與不可解析的隨機位址（NRPA）。序列埠每次掃描輸出一行 `STATS`，每個裝置再輸出一行 `DEV`（掃描次數、位址、類型、訊號、已持續秒數），OLED 改顯示統計表。

統計模式可以在執行中切換：序列埠送出 `stats on`、`stats off`（`stats` 查看目前狀態），或在手機面板按按鈕。開啟時從頭計數，記錄裡寫一行 `MODE,掃描次數,stats,on`，關閉時寫 `MODE,掃描次數,stats,off`，分析時用來切出統計的區段。切換後的設定存在 NVS，重新開機後維持，而且優先於程式裡 `STATS_MODE` 的預設值。

在住宅區量測 46 分鐘的結果：

- 同一個位址持續 20 分鐘以上的，只有鄰居家電的公開位址，最久 43 分鐘
- 手機的 RPA 大約 17 到 20 分鐘更換一次，量到最久的是 26.5 分鐘
- 隨機固定位址也會更換，房間裡的兩個裝置都是每 15 分鐘換一次，所以累計看到的不同位址數量會一直增加
- 換位址時，舊位址消失與新位址出現在同一次掃描，類型相同、訊號強度接近，一個裝置的多個位址會同時更換。依這個規律可以把同一個裝置前後的位址串起來，訊號很強的裝置都能串成完整的一條，但同時有好幾個裝置換位址、人又在移動時會串錯

### Wi-Fi 基地台掃描（`WIFI_SCAN`）

每次藍牙掃描之後，再被動掃描約 2 秒的 Wi-Fi。基地台的位置固定，周圍的基地台整批換掉代表人在移動，用來補足沒有 GPS 的限制，在室內與地下也有效。被動掃描只接收基地台的廣播，不送出探測封包，也不連線。

每個基地台輸出一行 `AP`（掃描次數、位址、訊號、頻道、名稱），每次掃描輸出一行 `WIFI`（掃描次數、看到幾個、第一次出現幾個、上一次也看得到幾個）。在住家不動時，每次約看到 30 到 40 個基地台，其中七到八成上一次也看得到，其餘是訊號微弱、時有時無的基地台。

### 人流計數模式（`CROWD_MODE`）

在捷運站這類公共場所量測經過的裝置數量時使用，與統計模式擇一。這個模式不記錄、不輸出任何原始位址：位址加上開機時產生的隨機鹽值後算 SHA-256，只保留雜湊值用來去除重複。鹽值只存在記憶體，重新開機就換掉，之後無法比對回原本的位址。路過的追蹤器不印位址，Wi-Fi 只輸出數量，不輸出個別基地台，因為手機開的個人熱點也在裡面。

每次掃描輸出一行 `CROWD`（掃描次數、看到幾個、第一次出現幾個、訊號強於 -70 dBm 幾個、四種位址類型各幾個），每 10 次掃描（約 5 分鐘）輸出一行 `CROWDW`（這段時間的不同裝置、其中新出現的、整段時間都在的）。

量到的是裝置，不是人。一個人可能帶好幾個裝置，待超過 15 分鐘的手機會換位址而被算成好幾個，沒帶藍牙裝置的人則算不到。絕對數字不準，每小時的起伏可以拿來比較。到車站量測時，人與板子要待在一起，不要把板子留在站內。

### 對時

板子沒有時鐘。接上電腦時從序列埠送出 `time <Unix 秒數>` 對時，之後每次掃描輸出一行 `CLOCK`（掃描次數、Unix 秒數）。換電源會重新開機，時間就不見了，要接上 DS3231 這類時鐘模組才能保留。

### flash 記錄（`LOG_TO_FLASH`）

序列埠的每一行同時寫進 flash 的 FAT 分割區，每次掃描完寫一次，斷電不會消失，上限 8 MB（統計模式下約 30 小時）。出門實測時沒有電腦接著，靠它保存資料。

接上電腦後，在序列埠送出指令：

| 指令 | 作用 |
|---|---|
| `dump` | 印出整份記錄，夾在 `=== FLASH LOG BEGIN ===` 與 `=== FLASH LOG END ===` 之間 |
| `clear` | 清空記錄 |
| `info` | 記錄的大小與剩餘空間 |
| `stats on`、`stats off` | 開啟或關閉統計模式 |
| `log on`、`log off` | 開始或暫停寫入 flash 記錄 |
| `quiet on`、`quiet off` | 安靜模式，蜂鳴器不響 |
| `link`、`link off` | 切換手機連線、全部關閉 |
| `preset 0` 到 `preset 3` | 警示門檻：敏感、標準、保守、快速測試 |
| `interval 15`、`30`、`60` | 掃描間隔（秒） |
| `duration 3`、`5` | 每次掃描的長度（秒） |
| `idle 0`、`5`、`10`、`30` | 手機連線閒置幾分鐘後自動關閉，0 不關閉 |
| `wifiscan on`、`wifiscan off` | Wi-Fi 基地台掃描 |
| `cfg` | 在記錄裡寫一行目前的設定 |
| `name 名稱` | 熱點與藍牙的名稱，最多 29 bytes |
| `pass 密碼` | 熱點密碼，8 到 63 個 ASCII 字元。自訂密碼不寫進記錄 |
| `led on`、`led off` | LED 開啟或全關 |
| `factory reset` | 恢復原廠設定，flash 記錄保留 |
| `sound 位址` | 讓追蹤器發出聲音，結果印在序列埠 |
| `blepin`、`blepin new` | 顯示或重新產生藍牙配對碼 |
| `ble unpair` | 清除所有配對過的手機 |
| `soundtest` | 主動掃描 5 秒，對廣播發聲服務的裝置（例如 `tools/tracker_sim.py` 模擬的追蹤器）執行發聲流程 |
| `place next` | 模擬換了地點，測試 Wi-Fi 移動判斷 |
| `places` | 列出存過的地點、名稱與來過幾次 |
| `place name 編號 名稱` | 替地點命名，編號 0 是目前所在的地點，名稱最多 30 bytes |
| `place forget 編號` | 刪除存過的地點 |
| `ota selftest` | 把執行中的韌體複製到另一個程式槽後從那裡開機，不用 Wi-Fi 也能驗證更新流程 |
| `netwifi 名稱`、`netpass 密碼` | 設定從網路更新時連線的 Wi-Fi，名稱可以有空格 |
| `netupdate` | 從 assets.anoni.net 下載更新，接著電腦代表有實體接觸，不必先按 BOOT |
| `autoupdate on`、`autoupdate off` | 打開或關閉自動更新，`autoupdate` 印出目前狀態與下次檢查的時間 |
| `autoupdate now` | 照自動更新的條件馬上檢查一次，延後的條件仍然有效 |

| `channel test`、`channel stable` | 從測試通道或正式通道更新，`channel` 印出目前的通道 |
| `json` | 印出手機面板讀取的狀態 JSON，不用手機也能檢查 |
| `history` | 印出警示歷史與時間軸用的 JSON |
| `history prev` | 印出存在 flash 的之前幾次開機的警示歷史（JSON 陣列，新的在前） |
| `history clear` | 刪除之前開機的警示歷史，這次開機的保留 |
| `mark 文字` | 打記號，文字可省略 |
| `ack` | 確認警示 |
| `find` | 等同雙擊 BOOT：尋找中就結束，否則尋找警示中或訊號最強的追蹤器 |
| `find 位址`、`find off` | 尋找指定的位址、結束尋找 |
| `oled dump` | 把 OLED 目前的畫面印成十六進位，沒接 OLED 也能用 |
| `oled demo 名稱` | 用假資料畫指定的畫面並印出，名稱是 `normal`、`alert`、`find`、`lost`、`room`、`roomdone`、`wifi`、`sound` 等，不帶名稱時列出全部 |
| `room`、`room stop` | 開始或取消房間檢查 |

Arduino IDE 的 Serial Monitor 上方有輸入框，輸入指令後按 Enter 即可。115200 鮑率下，一小時的統計記錄約 250 KB，`dump` 約需 20 秒。

沒有警示時按一下 BOOT 鍵，會在記錄裡寫一行 `MARK`（編號、掃描次數、開機後秒數），白燈閃一下。實測時在「出門」、「上車」、「下車」這些時間點按一下，分析時就能對上。

### 手機連線

出門實測時不必帶電腦。BOOT 鍵只負責開關：長按 2 秒，Wi-Fi 沒開就打開 Wi-Fi 熱點與手機面板（藍牙維持原狀），開著就全部關閉。藍牙連線的開關、只留藍牙，都在手機面板設定的「連線」切換，面板也寫出 Wi-Fi 與藍牙目前的狀態，不必記得按了第幾次。

| 狀態 | 怎麼進入 | 燈號 |
|---|---|---|
| 只有 Wi-Fi | 全部關閉時長按 BOOT | 每 3 秒亮 0.5 秒青色，蜂鳴器響 1 聲 |
| Wi-Fi 加藍牙 | 面板打開「藍牙連線」 | 每 3 秒亮 0.5 秒白色，響 2 聲 |
| 只有藍牙 | 藍牙開著時在面板關閉 Wi-Fi 熱點 | 每 3 秒亮 0.5 秒紫色，響 3 聲 |
| 全部關閉 | Wi-Fi 開著時長按 BOOT，或面板的「全部關閉」 | 綠燈，響一聲長音 |

按下 BOOT 時燈號立刻變成白色，表示有讀到按鍵。按滿 2 秒切換的瞬間，新狀態的顏色恆亮 2 秒，這時就可以放開。只有藍牙時長按 BOOT 會打開 Wi-Fi，變成 Wi-Fi 加藍牙，面板就能再連上，藍牙終端機送 `wifi on` 也可以。

短按 BOOT 仍然是確認警示或打記號，為了分辨雙擊，放開後 0.35 秒才執行（記號的時間用按下的那一刻）。雙擊 BOOT 開始尋找：只挑最近兩次掃描還在的追蹤器，有警示時找警示中的，沒有警示時找訊號最強的（已經離開的只有警示過才列入，排在後面），尋找中再雙擊就結束。附近沒有追蹤器時紅燈閃兩下、短嗶一聲，不打記號。切換時記錄裡寫一行 `LINK,掃描次數,wifi,on 或 off,ble,on 或 off`。開啟後 10 分鐘都沒有手機連著，自動全部關閉（`LINK_IDLE_OFF_MS`）。接著電腦時也可以從序列埠送 `link`（等同長按 BOOT）、`link wifi`、`link ble`、`link both`、`link off`。`WEB_PANEL` 設成 `true` 則開機就打開 Wi-Fi 面板。

Wi-Fi 與藍牙開著時，板子會對外發出熱點與藍牙廣播，周圍的裝置收得到，偵測器不再是完全被動的狀態，所以用完就關。

#### Wi-Fi 面板

預設的熱點名稱是 `BLE-Tracker-` 加上第一次開機時隨機產生的四碼，密碼 `anoni-tracker`，都可以在面板上修改。手機連上後自動跳出面板，沒跳出的話用瀏覽器開 `http://192.168.4.1`。

面板是為了單手在捷運上或走路時看一眼設計的。頂端用大字與底色顯示目前的狀態：青色「沒有發現」是附近沒有追蹤器，黃色「觀察中」是有追蹤器但還沒達到警示條件，紅色「警示」是有追蹤器符合全部條件，確認警示後追蹤器還在附近時是黃色「已確認」。手機連續 8 秒以上讀不到板子時改成灰色「連線中斷」，並寫出最後一次更新的時間，避免把舊的狀態當成現況。旁邊的訊號距離圖把你放在圓心，每個追蹤器是一個點，訊號越強越靠近圓心，同一個追蹤器固定在同一個方向，看得出它是不是越來越近，方向不代表實際方位。最上面一行寫出距離下一次掃描還有幾秒，掃描的 5 秒內寫「正在掃描」，訊號距離圖上有一道掃過的光（系統設定減少動態效果時不轉動），狀態區底部的細線是到下一次掃描的進度。房間檢查或更新韌體時掃描暫停，寫「等待下一次掃描」。狀態文字下方是周圍環境：上一次掃描收到幾個藍牙裝置（只計數，不記位址），開著移動判斷時加上 Wi-Fi 基地台數，進捷運站時會明顯變多。再下面一行顯示移動中或停留中、目前的地點，以及安靜模式、自動發聲這些會影響警示的設定。「附近的追蹤器」每一列有一條小折線，畫出最近 10 次出現時的訊號強度，並寫出訊號變強、變弱或穩定（後 3 次跟前 3 次的平均相差 4 dB 以上才算變化）。一直跟著你的追蹤器，訊號會穩定維持在某個強度，路人經過時則是一個尖峰後消失。操作分成五個分頁，放在畫面底部，拇指按得到：

- 偵測：附近的追蹤器與尋找、發聲
- 歷史：警示歷史、時間軸、蒐證摘要
- 記號：打記號、最近的記號、對時
- 房間：房間檢查與報告，見下方「房間檢查」
- 設定：偵測、警示與發聲、連線、flash 記錄、韌體

切到其他分頁時頂端縮成一行，警示時「確認警示」、「尋找它」、「讓它響」三個按鈕在每個分頁都留著。面板上可以：

- 附近的追蹤器：每個追蹤器的類型、位址、訊號、多久前出現，以及三個警示條件各自的進度條（出現時間、近距離次數、出現比例），一眼看出離警示還差多少。警示中的排在最前面
- 發出聲音：在追蹤器旁或尋找畫面按「讓它響」，板子短暫掃描 4 秒找到它、連線，送出 DULT 規格的 `Sound_Start`，結果顯示在面板上，記錄裡寫一行 `SOUND,掃描次數,位址,結果代碼,狀態碼`。見下方「讓追蹤器發出聲音」
- 尋找：在追蹤器旁按「尋找」，板子在兩次正式掃描之間持續做 1 秒的短掃描，畫面整個換成大字的訊號強度與長條，每秒更新，拿著板子走動找出位置。5 分鐘後自動結束，記錄裡寫一行 `FIND,掃描次數,位址`。不帶手機時雙擊 BOOT 也能開始尋找，蜂鳴器像蓋革計數器一樣，訊號 -45 dBm 以上每 0.1 秒嗶一聲，-95 dBm 以下每 1.2 秒一聲，LED 跟著閃白色，OLED 顯示大字的訊號強度。8 秒以上沒收到時不嗶，LED 改成藍色慢慢呼吸。安靜模式時只有燈號，燈號全關時只有嗶聲
- 警示歷史：追蹤器 30 分鐘沒出現會從清單移除，這裡另外保留整次開機觸發過警示的追蹤器，包含第一次出現、觸發警示、最後一次出現的時間與最強訊號，以及發聲的結果（成功、不支援 DULT、找不到、連不上、被拒絕，或觸發警示時自動發聲沒有作用），現場沒聽到聲音時可以從這裡看原因。使用快速測試門檻時，面板頂端會提醒容易誤報
- 重新開機後的歷史：接上電腦讀資料時，打開序列埠常會讓板子重新開機，所以警示歷史、時間軸與記號也存在 flash（`/hist_cur.json`）。警示、確認、發聲結果或記號一有變化就存檔，只有出現時段變長時每 5 分鐘存一次。開機時把上一次的紀錄移進 `/hist_prev.json`，最多保留 8 次開機、合計 96 KB，超過時先丟掉沒有警示也沒有記號的那幾次，記錄裡寫一行 `HIST,0,archived,保留幾次,bytes`。「歷史」分頁上方切換「這次開機」與之前每一次開機（有對時的顯示開機的日期時間），警示清單、時間軸與蒐證摘要都跟著切換。不想留在板子上時，在分頁底部刪除之前開機的紀錄，或序列埠送 `history clear`
- 時間軸：每個追蹤器出現的時段畫成橫條，觸發過警示的用紅色，打的記號畫成直線，可以切換最近 1 小時、3 小時或全部，看出追蹤器是不是上車後才出現、下車後還在
- 蒐證摘要：整理觸發警示的追蹤器、出現時段、期間的記號，以及判斷方式的限制（只依藍牙廣播判斷、AirPods 也會被列入、沒有 GPS 分不出是跟著你還是你待在它附近、位址不代表擁有者），可以截圖或複製給協助你的人
- 打記號：預設有「出門」、「上車」、「下車」、「進站」、「出站」、「到達」、「回家」等按鈕，也能輸入自訂文字。記錄裡多一個文字欄位，例如 `MARK,3,120,3605,上車`，時間用按下的那一刻。任何模式都有效，flash 記錄暫停時只保留在記憶體
- 確認警示：有警示時頂端變成紅色，Android 手機會震動，按「確認警示」等同短按 BOOT 鍵。新的警示寫進歷史時，「歷史」分頁會出現紅點
- 設定：警示門檻（敏感、標準、保守、快速測試四組）、掃描間隔與長度、手機連線閒置自動關閉的時間、移動判斷（Wi-Fi 基地台掃描）、統計模式、flash 記錄的寫入（暫停時也能下載舊記錄）、安靜模式（警示時蜂鳴器不響）、連上熱點時自動跳出面板、板子的燈號。對時在「記號」分頁。設定都存在 NVS，比程式裡的預設值優先，序列埠也能切換。切換門檻時追蹤器的紀錄會清空重新累計，避免同一個追蹤器的次數混用兩套門檻。每次變更都在記錄裡寫一行 `CFG`，列出當時的門檻與掃描節奏
- flash 記錄的內容：下載整份記錄檔、看最後約 3 KB、刪除（按兩次確認）。在自動跳出的小視窗裡可能無法下載，要改用瀏覽器開
- 隱蔽與安全：熱點與藍牙的名稱可以改成不起眼的名稱（例如 `TP-Link_Extender`），周圍的人就不容易從名稱看出你帶著偵測器。名稱最多 29 bytes，是熱點名稱與藍牙廣播名稱共同的上限。熱點密碼可以改成 8 到 63 個 ASCII 字元，預設密碼寫在這份 README，知道的人都能連上，建議修改。LED 可以全關，搭配安靜模式時板子本身完全沒有提示，警示改從手機面板與藍牙連線推送
- 恢復原廠設定：名稱、密碼、門檻、存過的地點與所有設定回到預設值。flash 記錄與警示歷史保留，但警示歷史（包含之前開機的紀錄）裡存的地點名稱會清掉，只留地點編號。面板按兩次「恢復」、序列埠送 `factory reset`，或長按 BOOT 10 秒（5 秒起燈號快閃黃色，10 秒後改成白色快閃，這時放開）。按著 BOOT 重新開機會進入燒錄模式，所以放開後才執行
- 韌體更新：不必接電腦，在面板上傳建置好的 `firmware.bin`（在 `.pio/build/esp32-s3-n16r8/`）。為了避免附近的人上傳惡意韌體，按「開放更新」後要在 60 秒內短按一下板子的 BOOT 鍵（燈號快閃紫色），才會開放 5 分鐘的上傳時間（打開自動更新時，這顆按鈕叫「開放上傳」）。韌體寫進另一個程式槽，驗證格式、晶片型號與雜湊通過才切換，上傳期間藍牙掃描暫停。重新開機後自動打開 Wi-Fi 面板，面板上的版本號、建置時間與程式槽（`app0`、`app1` 輪流）用來確認換成新版。之後再用 USB 燒錄時會重寫程式槽的紀錄，照常從 USB 燒進去的版本開機
- 版本號：建置時把 git 的 commit 編號寫進韌體（`platformio.ini` 的 `FW_REV`，有還沒 commit 的變更時加上 `-dirty`，用 Arduino IDE 建置時顯示 `dev`）。面板每個分頁的最下方都顯示名稱、版本號與建置時間，開機時序列埠印出 `BUILD,建置時間,程式槽,版本號`
- 從網路更新：開放更新的 5 分鐘內，也可以按「從網路更新」的「檢查並安裝新版」，不必先把檔案傳到手機。板子用設定裡「更新用的 Wi-Fi」連上網（家裡或辦公室的基地台，ESP32-S3 只支援 2.4 GHz）。iPhone 連著板子的熱點時無法同時開個人熱點給板子上網，要用其他基地台。板子經由 HTTPS 讀取 `https://assets.anoni.net/esp32-tracker/latest.json`，建置時間跟自己相同就回報已經是最新版，不同才下載 `latest.json` 指定的檔案，邊寫進另一個程式槽邊算 SHA-256，跟 `latest.json` 相符才切換。網址寫死在程式裡，面板不能改，知道熱點密碼的人也只能裝上社群發布的版本。連上基地台時熱點會換到基地台的頻道，手機可能斷線幾秒，重新連上後面板顯示下載進度。記錄裡寫 `OTA,掃描次數,net_start`，結束時寫 `net_done`、`net_latest` 或 `net_fail` 與原因
- 自動更新：在設定的「韌體」打開「自動更新」（預設關閉，要先設定更新用的 Wi-Fi），打開時要在 60 秒內短按 BOOT 確認（燈號快閃紫色），之後從網路更新就不必再按。接收測試版也一樣，打開時要按 BOOT，關閉不必。這兩個設定會讓板子自己換上網路上的韌體，知道熱點密碼的人不能只靠面板打開。序列埠的 `autoupdate on`、`channel test` 不必按，接著電腦代表有實體接觸。板子開機 90 秒後第一次檢查，之後每 6 小時一次：先被動掃描，附近有更新用的 Wi-Fi 才連上 assets.anoni.net，流程跟按「檢查並安裝新版」相同，只裝比目前新、SHA-256 相符的版本，裝好直接重新開機，不打開熱點。附近沒有這個 Wi-Fi 時 30 分鐘後再掃描一次，下載失敗 1 小時後再試。有還沒確認的警示、有追蹤器離警示過半、房間檢查、尋找、發聲、按過 BOOT 等待上傳，或手機連著熱點時先不檢查，每 30 秒再看一次，避免重新開機打斷偵測或正在看的面板。手機連著板子的熱點時，iPhone 的個人熱點沒辦法替板子上網（DNS 會通，連線失敗），把個人熱點設成更新用的 Wi-Fi 時，打開自動更新、手機離開板子的熱點，板子會在 30 秒內自己連上去更新。個人熱點要打開「允許其他人加入」才會一直廣播名稱，被動掃描才看得到。打開之後，韌體一節多一個「從網路更新」的「檢查並安裝新版」，可以隨時手動檢查，原本的「開放更新」改名為「開放上傳」，只剩上傳檔案要用。上傳手機裡的檔案仍要按 BOOT。記錄寫 `OTA,掃描次數,auto_on` 或 `auto_off`，檢查結果寫 `auto_latest`、`auto_fail`、`auto_nonet`（連續發生只記一次）或 `auto_done`，重新開機後寫 `OTA,0,auto_ok,版本,from 舊版本`。換上的版本跟下載的不同時寫 `auto_mismatch`，之後不再自動安裝那個版本。隱藏名稱的 Wi-Fi 在被動掃描裡沒有名稱，自動更新找不到，只能手動更新

- 網址更新與記憶體：TLS 交握要約 40 KB 的連續空間，ESP-IDF 預設只放內部 RAM。板子開著藍牙、熱點與面板運作久了，內部 RAM 會被切碎（2026-11-27 B 板只剩 33 KB，更新失敗）。更新期間改成優先放 PSRAM（`mbedtls_platform_set_calloc_free`），結束後換回預設。面板「韌體更新」一列寫出目前的記憶體，flash 記錄每 10 分鐘、開機與每次網址更新開始時寫一行 `MEM,掃描次數,原因,內部剩餘,內部最大連續,內部開機以來最低,PSRAM 剩餘,PSRAM 最大連續,追蹤器筆數,歷史筆數,存過的地點`（單位 bytes，原因是 `boot`、`tick`、`net`、`auto` 或 `cmd`），用來找出哪個功能吃記憶體、運作多久開始切碎

  打開自動更新代表信任 assets.anoni.net 上發布的韌體：發布的伺服器被入侵時，惡意韌體會在幾小時內裝進板子，不必有人按 BOOT。需要每一版都自己確認的話維持關閉，用「開放更新」加 BOOT 手動更新
- 關閉 Wi-Fi 與藍牙：在設定的「連線」按「關閉」，板子停止對外發出訊號，回到只做被動掃描

第一次打開面板時會自動用手機的時間對時。

網頁伺服器在另一個核心執行，藍牙掃描的 5 秒內也能操作。同時打開 `WIFI_SCAN` 時，每次掃描 Wi-Fi 的約 2 秒內熱點會暫停回應，面板會提示再按一次。iPhone 關掉自動跳出的視窗時會直接斷線，除非在「取消」後選「不使用網際網路」。要長時間連著的話，在面板設定的「連線」關掉「連上熱點時自動跳出面板」（設定存在 NVS），重新連線後手機會顯示「沒有網際網路連線」並維持連線，面板改用瀏覽器開 `http://192.168.4.1`。Android 會詢問要不要保持連線，選擇保持連線即可。

#### 藍牙連線

藍牙名稱與熱點相同，提供 Nordic UART Service（NUS）的文字通道，不佔用手機的 Wi-Fi。連線要先配對：第一次送出指令時手機跳出配對視窗，輸入 6 位數的配對碼。配對碼第一次開機時隨機產生、存在 NVS，顯示在 Wi-Fi 面板設定的「連線」與序列埠（`blepin`），不寫進記錄。連線加密並通過驗證之前，板子不接受指令，也不送出任何文字。配對過的手機之後自動連線，面板可以重新產生配對碼或清除已配對的手機，恢復原廠設定也會一併清除。Android 用 Serial Bluetooth Terminal，iOS 用 Bluefruit Connect 的 UART 或 nRF Toolbox 連線後輸入指令：

| 指令 | 作用 |
|---|---|
| `help` | 列出指令 |
| `status` | 掃描次數、追蹤器、警示、統計模式、flash 記錄、是否已對時 |
| `mark 上車` | 打記號，文字可省略 |
| `ack` | 確認警示 |
| `trackers` | 附近的追蹤器與離警示門檻多遠 |
| `sound 位址` | 讓追蹤器發出聲音，省略位址時選尋找中、警示中或訊號最強的 |
| `history` | 自開機以來觸發過警示的追蹤器 |
| `stats on`、`stats off` | 切換統計模式 |
| `log on`、`log off` | flash 記錄的寫入 |
| `quiet on`、`quiet off` | 安靜模式 |
| `time 1795500000` | 用 Unix 秒數對時 |
| `wifi` | 熱點的名稱、密碼，以及可以做成 QR code 的 `WIFI:` 文字，用來加入 Wi-Fi 面板 |
| `wifi on`、`wifi off` | 開關 Wi-Fi 熱點與手機面板 |
| `off` | 關閉藍牙與 Wi-Fi，回到單純偵測 |

熱點、藍牙與掃描共用同一組 2.4 GHz 射頻。Wi-Fi 開著時，藍牙掃描只用三成的時間（`SCAN_WINDOW_WIFI_MS`），手機連入後 15 秒內先不掃描（`JOIN_GRACE_MS`），讓手機順利取得 IP、跳出頁面。追蹤器約每 2 秒廣播一次，5 秒的掃描仍收得到，但同一段時間掃到的裝置會略少，分析統計資料時用 `LINK` 那幾行切出 Wi-Fi 開著的區段。

### Wi-Fi 移動判斷

打開 Wi-Fi 基地台掃描後，用周圍基地台的變化判斷你換了地點：這次掃描到的基地台，不到三成出現在目前地點看過的基地台裡，就算換了地點（記錄裡寫一行 `PLACE,掃描次數,地點編號,重疊比例,基地台數,new 或 revisit,跟最像的指紋重疊的比例`）。基地台少於 3 個時（地下、郊外）不判斷。追蹤器要在至少 3 個不同地點都出現才警示，跟 Kismet 用 GPS 要求 3 個相距 100 公尺以上地點的做法相同。面板的每個追蹤器多一條「經過地點」的進度，狀態列顯示「移動中」或「停留中」。

用實際記錄驗證過參數（下表是加上地點指紋之前的算法：回到同一個地點也算一個地點。改成計算不同的地點之後，只在兩個地點之間、中間沒有掃描到基地台的路段時，追蹤器不會湊滿 3 個地點，數字還沒重算）。2026-11-24 A 板帶著 Wi-Fi 掃描的一整天：兩個長時間停留的地方各約 800 次掃描，都沒有誤判成換地點，移動途中判斷出約 28 次換地點（基地台太少的路段不判斷）。用同一份記錄重算警示數：

| 資料 | 門檻 | 原本 | 加上移動判斷與 Apple 自家裝置的規則 |
|---|---|---|---|
| A 板一整天（有 Wi-Fi 資料） | 快速測試 | 67 | 14 |
| | 標準 | 9 | 1 |
| B 板 2026-11-25（沒有 Wi-Fi 資料，只排除 Apple 自家裝置） | 快速測試 | 128 | 15 |
| | 標準 | 79 | 1 |

另一份資料，B 板 2026-11-24 停在同一個地方連續 16 小時、2412 次掃描，換地點 0 次，最低的重疊比例是 72%，離 30% 的門檻還很遠。參數只用這兩份資料驗證過，不同的路線與環境（例如郊區、基地台很少的地方）還需要更多資料。序列埠的 `place next` 可以模擬換地點，測試時使用。

### 認得回到原處的地點

換地點時，板子會跟存過的地點指紋比對，認得出來就沿用原本的編號，可以在面板的「設定 → 偵測 → 地點」替目前的地點命名（家、公司、捷運站）。追蹤器「經過的地點」改成計算不同的地點，在家與公司之間來回不會被算成好幾個地點。警示歷史與複製的摘要會寫出追蹤器跟著你依序經過哪些地點，例如「家 → 地點 #14 → 公司」。

- 停留約 5 分鐘（10 次掃描）以上的地方才存成指紋，通勤途中一閃而過的地方不存。最多存 32 個地點，滿了先移除最久沒去、沒有命名的
- 每個地點存出現最穩定的 24 個基地台，跟新的掃描至少有 3 個共同的基地台、而且佔較少那邊的 40% 以上，才算同一個地點。只看比例的話，捷運地下段每次只掃到一兩個基地台，很容易誤判
- 隨機位址（locally administered）的基地台不收進指紋，那多半是跟著人移動的手機熱點
- BSSID 加上每塊板子自己的隨機鹽做雜湊才存，不能直接貼到公開的基地台資料庫查詢，不同板子的指紋也比對不起來。鹽跟指紋存在同一個檔案（`/places.txt`），取得板子的人仍可以拿公開的基地台清單逐一算雜湊比對、推出地點，這只是提高門檻，不是加密
- 名稱存在 `/places.txt`，不寫進 flash 記錄（記錄裡只有地點編號）。警示歷史存檔時會一起存下當時的名稱，所以之前開機的紀錄與複製的摘要裡也看得到。恢復原廠設定時刪除 `/places.txt`，警示歷史是舉證用的，保留，但裡面的地點名稱會清掉（`places::stripNames`）
- 程式在 `places.h`，不依賴 Arduino，單元測試編譯同一份（`tests/unit/test_places.cpp`）

2026-11-27 用 A 板 11/24 的實測記錄離線模擬：晚上回到早上出發的地方時，跟早上存的指紋重疊 90%，認成同一個地點。兩個白天停留的地方重疊 12%，判成不同地點。整天只存了 3 個停留夠久的地點，移動途中約 30 次換地點都沒有存。只有這一份有往返的資料，郊區、基地台很少的地方還要更多實測。

flash 記錄裡的 `AP,…` 行仍然存著完整的 BSSID 與名稱，取得記錄檔的人可以查出你去過的地方。地點指紋已經改用雜湊，記錄的格式之後再改。

### 會議室檢查

閉門會議收走手機之後，面板「空間」分頁的「會議室檢查」監看房間裡有沒有還開著藍牙或 Wi-Fi 的裝置。開始後 2 分鐘建立基準，記下這時收得到的藍牙裝置（多半是隔壁、走廊或房間裡固定的設備），以及近距離 Wi-Fi 探測請求的頻率與指紋。基準時多收門檻下 10 dB 的裝置，訊號在門檻上下徘徊的才不會在監看時被當成多出來的（2026-11-27 A 板實測，沒有人移動也冒出 3 個）。之後持續監看，只在面板提醒，不嗶、不亮警示燈：

- 藍牙：基準之外出現新的強訊號裝置就列出來，標出是 Apple、Android 與 Google、Samsung、Windows 與 Microsoft 或其他裝置，可以按「尋找」找出位置。iPhone、Mac 的藍牙位址約 15 分鐘換一次，同一類的基準裝置剛消失時，把新出現的當成同一台換了位址，不提醒
- Wi-Fi：隔壁、門外的手機也會不定時找 Wi-Fi，動靜比藍牙雜，所以只標成黃色的「留意」，不跟多出藍牙裝置的紅色「提醒」同一個等級。最近每分鐘的近距離請求超過基準的 2 倍再加 2 個（至少 3 個），或基準時沒有的指紋收到 2 次以上，才標成留意。A 板實測，家裡沒有人移動時，1 分鐘的基準記不全，探測請求也會一陣一陣地變多
- 範圍分近（-60 dBm）、中（-70 dBm，預設，大約同一個房間）、遠（-80 dBm）。檢查期間藍牙每 10 秒掃描一次
- 每個多出來的藍牙裝置列出類型與型號、廣播的名稱、使用中的跡象、訊號的變化與出現的時間：
  - 類型：Apple 的 Continuity 廣播分得出手錶（活動碼「手錶戴著、已解鎖」）、有行動網路的 iPhone 或 iPad（可以分享個人熱點）、AirPods 與 Beats 的型號。Microsoft 的 CDP 信標分得出 Windows 筆電、桌機與裝了「手機連結」的 iPhone、Android。Google Fast Pair 的配件有型號編號
  - 使用中的跡象：Apple 的 Handoff 代表正在用支援接續互通的 App（1 分鐘內標成「正在使用」，之前的寫「會議中用過」），AirDrop 開著，Apple 的活動碼（螢幕亮著、通話中或 FaceTime、播放影片等）
  - 訊號：最近 10 次的訊號畫成小折線，越來越強代表越靠近
  - 時間軸：從開始檢查到現在，每個多出來的裝置什麼時候出現、什麼時候離開，可以對照會議的流程
- 在找 Wi-Fi 的裝置依探測請求的指紋分組：支援的速度、HT、VHT、HE、延伸功能等欄位的組合，同一支手機換了隨機位址也相同，估計有幾種裝置在找 Wi-Fi。出現基準時沒有的指紋也會提醒。部分 Android 手機與 Windows 筆電在探測請求裡帶 WPS 資訊，列出廠牌、型號與裝置名稱。同一種型號的手機指紋可能相同，會被算成一組
- 格式的來源：Microsoft 的 MS-CDP 公開規格、Wi-Fi Simple Configuration（WPS）規格、Google Fast Pair 文件。Apple 的 Continuity 沒有官方規格，依 Celosia 與 Cunche〈Discontinued Privacy〉（PETS 2020）與 hexway apple_bleee 的逆向研究，面板上標成「估計」
- AirDrop 廣播裡有電話號碼與 email 的雜湊片段，只記下「AirDrop 開著」，不解析雜湊。藍牙廣播的名稱與 WPS 的裝置名稱常帶主人的名字，只放在記憶體、顯示在面板，不寫進 flash 記錄、不印到序列埠。結束檢查後結果留在面板，下一次開始檢查或重新開機時清除
- 偵測不到的：只開行動網路、Wi-Fi 與藍牙都關掉的手機（4G、5G 不在板子收得到的 2.4 GHz），沒有無線功能的錄音設備。iPhone 開飛航模式時，如果之前在飛航模式下打開過 Wi-Fi 或藍牙，會一直保持開著，這種收得到
- 收走的手機最可靠的放法是屏蔽袋或屏蔽盒，這個檢查也可以用來確認屏蔽有沒有效：手機放進去之後，板子應該收不到它
- 位址只用雜湊比對，藍牙的原始位址只放在記憶體給「尋找」用，不顯示也不記錄。flash 記錄只寫開始、提醒與結束：`MEETING,掃描次數,start,門檻`、`MEETING,掃描次數,alert 或 clear,多出的裝置數,每分鐘的近距離探測請求`、`MEETING,掃描次數,done,分鐘,門檻,同時多出的裝置最多幾個,近距離的探測請求數`
- 事先告訴與會者會做無線訊號檢查，只看有沒有裝置，不記錄身分
- 序列埠：`meeting start -70`、`meeting stop`，`meeting` 印出目前的總數。判斷在 `meeting.h`，不依賴 Arduino，單元測試編譯同一份（`tests/unit/test_meeting.cpp`）

### 周圍手機洩漏的 Wi-Fi 名稱

手機找 Wi-Fi 時會送出探測請求（probe request）。只問「附近有誰」的請求不帶名稱，有些手機會直接問存過的網路，名稱（家、公司、住過的旅館）就跟著送出來，附近的人都收得到。面板「空間」分頁的「周圍手機洩漏的 Wi-Fi 名稱」統計一個空間有多少這樣的資訊：

- 監聽 5 分鐘，停在熱點的頻道，面板照常可以用。手機找 Wi-Fi 時會輪流掃過每個頻道，停在一個頻道也收得到。熱點沒開時停在頻道 6
- 統計收到幾個探測請求、來自幾個位址、其中幾個是固定位址（沒有隨機化，在不同地點都認得出是同一支手機），以及帶出了哪些名稱、各有幾個來源送出。新的手機多半每次掃描都換隨機位址，位址數會比實際的手機多
- 位址不存原文，只用開始監聽時隨機產生的鹽算出雜湊來計數。名稱只放在記憶體、顯示在面板（研究期間顯示完整名稱），不寫進 flash 記錄，也不印到序列埠。停止後結果留在面板，下一次開始監聽或重新開機時清除
- flash 記錄在結束時寫一行 `PROBE,掃描次數,done,秒數,頻道,請求數,來源數,固定位址數,帶名稱的請求數,不同的名稱數,丟掉的封包數`，沒有位址也沒有名稱
- 監聽期間不掃描 Wi-Fi 基地台（移動判斷暫停），不自動更新。開始房間檢查、尋找 Wi-Fi 裝置或網址更新時，監聽會先停止
- 序列埠：`probes start`、`probes stop`，`probes` 印出目前的總數（不印名稱）。解析與統計在 `probes.h`，不依賴 Arduino，單元測試編譯同一份（`tests/unit/test_probes.cpp`）

### 讓追蹤器發出聲音

尋找模式用訊號強度找到大概的位置後，讓追蹤器自己響，就能找出藏在包包夾層或車上的哪裡。板子短暫掃描 4 秒找到這個位址，先確認它的廣播接受連線（不接受就立刻回報，不白等逾時），連上後依序嘗試四種發聲協定，第一個找得到服務的就用它：

| 協定 | 服務 | 特徵值 | 開始 | 停止 |
|---|---|---|---|---|
| DULT | `15190001-12F4-C226-88ED-2AC5579F2A85` | `8E0C0001-1D68-FB92-BF61-48377421680E` | `00 03`，等 `Command_Response` | 追蹤器回報 `Sound_Completed` |
| AirTag 原始協定 | `7DFC9000-7D1C-4951-86AA-8D9728F8D66C` | `7DFC9001-7D1C-4951-86AA-8D9728F8D66C` | `AF` | 響完自己斷線 |
| Apple Find My | `0xFD44` | `4F860003-943B-49EF-BED4-2F730304427A` | `01 00 03` | `01 01 03` |
| Pebblebee | `0xFA25` | `0x2C02` | `01`（不等回應） | `02` |

DULT 依據 [draft-ietf-dult-accessory-protocol-01](https://datatracker.ietf.org/doc/draft-ietf-dult-accessory-protocol/) 的 3.11 與 3.13.4 節，其他三種參考 [AirGuard](https://github.com/seemoo-lab/AirGuard) 的 `AppleFindMy.kt`、`AirTag.kt`、`AirPods.kt`、`PebbleBee.kt`。嘗試順序跟 AirGuard 一樣：AirTag 先試原始協定，AirPods 先試 Find My，其他先試 DULT。響約 10 秒後停止。記錄裡寫一行 `SOUND,掃描次數,位址,結果代碼,狀態碼,連線錯誤碼,協定`。過程中主程式會停住約 5 到 20 秒，手機面板照常回應，背景的掃描會先停下來，結束後恢復。假追蹤器 `fa:ke:00:00:00:01` 只回傳模擬的結果。

2026-11-25 一整天的實測，自動發聲試了 336 次都沒成功：310 次連不上、29 次找不到、4 次連得上但當時只檢查 DULT 服務。那時還沒有連線前的檢查，也只對 DULT 嘗試，對象又幾乎都是路人的 iPhone、Mac。現在自動發聲只對可能響得起來的追蹤器：收過 DULT 廣播的、AirTag 與 Pebblebee，而且廣播接受連線。AirPods 可能正戴在別人耳朵上，不自動發聲，手動按「發出聲音」時才嘗試。其餘追蹤器在警示歷史標示「自動發聲跳過」。

四種協定用 `tools/tracker_sim.py` 驗證過：在 Mac 上用藍牙模擬追蹤器的發聲服務，偵測器的序列埠送出 `soundtest`，實際連線寫入。偵測器寫出的內容與上表一致，DULT 收到成功回覆與播放完畢後回報成功，收到 `0xFFFF` 時回報拒絕。模擬驗證的是偵測器端的實作，真的 AirTag、Pebblebee 會不會響，還要用實際的追蹤器確認。

2026-11-26 的實測，兩個真的 DULT 追蹤器回覆了成功（狀態 `0x0000`），DULT 發聲在實際的追蹤器上可以用。但那天用的是敏感門檻、沒開移動判斷，兩次都在辦公室裡，訊號約 -87 dBm（十公尺上下），追蹤器多半放在附近的抽屜或桌上，旁人聽到也分不出是誰的，發聲幫不到任何人。所以自動發聲改成三種：

| 自動發聲 | 什麼時候響 |
|---|---|
| 關閉 | 只有手動按「讓它響」 |
| 跟著我移動時（建議） | 開著移動判斷、追蹤器跟著你經過好幾個地點而觸發警示。同一班車上被放了追蹤器的乘客，追蹤器也會跟著經過好幾站，一樣會響 |
| 也協助周圍的人 | 再加上：與主人分開的 DULT 追蹤器在很近的距離（訊號強於 -70 dBm）出現超過 10 分鐘 |

DULT 規定主人的手機在附近時，追蹤器要拒絕非擁有者的發聲指令，所以會響的都是不在主人身邊的追蹤器，讓它響正是規格設計的用途。協助周圍的人等於替旁人決定讓他的包包響起來，聽到的人不一定知道原因，也可能是借來的東西或主人的手機沒電，所以要自己打開，面板上看過說明、按「我了解，開啟」才生效。

不管哪一種，每個追蹤器在重新開機前最多自動響一次（失敗時最多重試 3 次），響之前蜂鳴器嗶兩聲、藍牙連線推送一則訊息，提醒帶著板子的人留意四周。移動判斷沒開時，「跟著我移動時」不會作用，面板頂端會提醒。記錄裡的 `AUTOSOUND` 多一欄 `follow`（跟著你）或 `help`（協助周圍的人）。序列埠與藍牙終端機用 `autosound 0`、`1`、`2` 切換，`autosound on`、`off` 等於 `1`、`0`。2026-11-26 以前開著自動發聲的板子，更新後變成「跟著我移動時」。

### 房間檢查

住旅館、民宿時，進房間先用它檢查一遍：列出附近的 Wi-Fi 與藍牙裝置，標出可能是攝影機的裝置，每一個都寫出判斷理由，讓使用者自己決定要不要找出來。會擔心房間裡有攝影機的人，通常也在意行李裡被放了追蹤器，所以做成同一份韌體的一個模式，到了房間不必換韌體。程式在 `roomcheck.h`，不碰追蹤器的警示邏輯，報告不觸發蜂鳴器，也不算進警示。

在面板的「空間」分頁按「開始檢查」，或從序列埠、藍牙終端機送 `room`。整個檢查約 2 分鐘，依序是：

1. 藍牙主動掃描 15 秒，收集附近的藍牙裝置與名稱。名稱常放在掃描回應裡，被動掃描收不到，所以只有這 15 秒送出掃描請求，請求裡只帶板子的隨機位址
2. 關掉熱點（手機會斷線），掃描一次基地台，記下有基地台的頻道
3. 射頻切到監聽模式（promiscuous），在這些頻道輪流停留 3 輪，共約 105 秒。頻道少時每次停久一點，最長 15 秒
4. 恢復原本的 Wi-Fi 狀態，熱點開著的話重新打開，燈號綠色連閃兩下。手機連回熱點後，面板自動切到報告

檢查期間追蹤器偵測暫停，結束後自動恢復，短按 BOOT 可以中途取消。手機斷線時面板頂端顯示「房間檢查中」與剩下的時間，不會顯示成連線中斷。

判斷用三種線索，比對到就寫進理由：

| 線索 | 怎麼判斷 | 等級 |
|---|---|---|
| 攝影機品牌 | MAC 位址前三碼（OUI）、藍牙的公司代碼或服務 UUID 屬於 Hikvision、Dahua、EZVIZ、Wyze、Arlo、Ring、Reolink、小蟻、創米等 22 個攝影機品牌 | 建議找出來 |
| IoT 模組廠 | 屬於 Espressif、Tuya、Beken、AltoBeam、必聯（LB-LINK）等晶片或模組廠。便宜的 Wi-Fi 攝影機常用，插座、燈泡、感測器也用 | 可以留意 |
| 持續上傳 | 監聽的 3 輪裡至少 2 輪，送出的資料每秒超過 12 KB（約 96 kbps），而且送出是收到的 2 倍以上。影像串流的上傳量穩定而且大，視訊通話這類雙向的流量不會符合 | 固定位址的建議找出來，隨機位址（多半是手機、電腦）的可以留意 |
| 名稱像攝影機 | 熱點或藍牙的名稱含有 `ipc`、`cam`、`camera`、`dvr`、`v380`、`yoosee` 等字，或是 V380 系列的 `MV` 加一串數字 | 建議找出來 |

訊號弱於 -80 dBm，或監聽期間沒收到裝置自己送出的資料（訊號不明）時，多半在隔壁或更遠，最多列為「可以留意」，理由裡寫明原因。

報告裡每個標出來的裝置旁有「尋找」，按下後畫面換成全螢幕的訊號強度，板子的 OLED、嗶聲與燈號跟尋找追蹤器時相同。藍牙裝置直接用尋找模式。Wi-Fi 裝置要讓射頻停在它的頻道：熱點開著時先把熱點換到那個頻道（手機斷線幾秒再自動連回），再打開監聽，只記下這個位址送出的封包的訊號，所以裝置要有在傳資料才收得到。尋找時面板與記錄都不顯示位址，記錄寫的是 `FIND,掃描次數,room_種類,報告裡的編號`。序列埠用 `room find 編號`。報告下方另外寫了常見的藏匿位置、用手電筒找鏡頭反光，以及找到之後不要拆、先拍照、聯絡業者或報警。

速率是除以「停在那個裝置所在頻道的時間」算的，相鄰頻道漏收到的封包不計。廠商清單由 `tools/make_roomcheck_ids.py` 從 IEEE 的 OUI 登記資料與藍牙 SIG 的 assigned numbers 產生 `roomcheck_ids.h`，檔頭寫著下載日期，要增減廠商時改腳本裡的 `VENDORS` 再執行一次。

能找到與找不到的範圍也寫在面板的報告下方：

- 只找得到用無線網路的攝影機。接網路線、只錄在記憶卡、或關著 Wi-Fi 的找不到
- ESP32-S3 只收得到 2.4 GHz，只用 5 GHz 的裝置不會出現
- 很多攝影機只在偵測到動作、或有人在看的時候才上傳，檢查時沒在上傳的只能靠廠商與名稱判斷
- 板子只有一支天線，也不支援 Wi-Fi 6，雙天線同時傳或用 Wi-Fi 6 傳的封包解不開，這類裝置的上傳量會算少。便宜的攝影機多半是單天線的 802.11n，不受影響
- 隔壁房間、走廊的裝置也會列出來，訊號強度可以參考遠近
- 比對到廠商的不一定是攝影機，改過位址或名稱的裝置也比對不出來

監聽會收到同住的人、隔壁房客手機的 MAC 位址。報告、面板與 `room report` 只顯示廠商、名稱與判斷理由，flash 記錄只寫一行不含位址的摘要 `ROOM,掃描次數,done 或 cancelled,基地台數,連網裝置數,藍牙裝置數,建議找出來,可以留意,秒數`。面板的「記錄裝置的位址」（或 `roomlog on`）打開時，才另外寫 `ROOMDEV,掃描次數,種類,位址,等級,訊號,頻道,上傳 B/s`。

2026-11-26 在住處用 B 板實測，熱點關著與開著各檢查一次，約 2 分鐘完成：17 到 19 個基地台、6 到 11 個連網裝置、18 到 23 個藍牙裝置，兩個 IoT 模組廠的裝置列為可以留意（訊號 -86 與 -92 dBm，應該是鄰居的），沒有持續上傳的裝置。熱點在檢查後自動打開，追蹤器偵測 5 秒後恢復，`room stop` 在監聽中途取消時熱點也立刻恢復。同一天晚上用 A 板與 iPhone 實際操作，檢查完成後 iPhone 自動連回熱點、在跳出的視窗裡看到報告。持續上傳的門檻還沒有用真的 Wi-Fi 攝影機驗證，Android 也還沒試過。尋找 Wi-Fi 裝置在 B 板上對一個訊號 -60 dBm 的基地台實測，熱點開著與關著時訊號都持續更新。

## 隱私設計

預設的偵測模式：

- 只做被動掃描，不連線，也不送出掃描請求，旁人無法得知你帶著它（長按 BOOT 開啟手機連線、房間檢查的 15 秒藍牙主動掃描例外）
- 手機、耳機、手錶等不符合追蹤器特徵的裝置不記錄
- 紀錄只存在記憶體，斷電即消失，程式不開 WiFi，也不上傳任何資料
- 只有在面板按「檢查並安裝新版」（或序列埠送 `netupdate`），或打開自動更新後被動掃描看到設定的 Wi-Fi 時，才連上那個 Wi-Fi。自動更新只被動聽基地台的 beacon，不送出帶著 Wi-Fi 名稱的探測請求，不在家時不會對外透露家裡的 Wi-Fi 名稱。連上後只送出讀取 `latest.json` 與韌體的兩個 HTTPS 請求，結束後立刻斷開。更新用的 Wi-Fi 密碼只存在板子的 NVS，不寫進記錄，面板也只顯示名稱，恢復原廠設定時一併清除

打開手機連線時，板子會對外發出熱點與藍牙廣播，所以位址也要跟手機一樣隨機更換，避免有人用 Wi-Fi 或藍牙掃描工具在不同地點認出同一塊板子：

- 藍牙對外使用 RPA（可解析的隨機位址），約 15 分鐘換一次。配對時把解析金鑰（IRK）交給手機，配對過的手機仍認得出板子、自動重連。主動連線追蹤器發聲時也用 RPA
- 熱點每次開啟都換一組隨機的 BSSID（本地管理、單播位址）。手機是用名稱加入熱點，換 BSSID 不影響連線
- 預設名稱的後綴是第一次開機時隨機產生的四碼，不用 MAC 末四碼，恢復原廠設定時重新產生
- 晶片出廠的固定位址只在序列埠的開機訊息顯示（藍牙識別位址），用來分辨工作坊裡的每一塊板子，不會對外廣播

警示歷史存在 flash 裡，包含追蹤器的位址與出現時段，flash 記錄關著時也會保存，方便重新開機後舉證。把板子借給別人或送修之前，先刪除之前開機的紀錄。

研究用的模式會保留周圍所有裝置的完整位址，打開 flash 記錄時還會存下來。這是為了量測與蒐證，記錄檔只留在自己的電腦，不放進版控，也不公開。

會議室檢查與「周圍手機洩漏的 Wi-Fi 名稱」會顯示周圍裝置廣播的名稱、WPS 的裝置名稱與手機找過的 Wi-Fi 名稱，這些常帶著主人的名字或去過的地方。名稱只放在記憶體、顯示在面板，不寫進 flash 記錄，也不印到序列埠。結束後結果留在面板，下一次開始或重新開機時清除。裝置的位址用加鹽的雜湊比對，鹽值每次開始檢查時重新產生。會議室檢查另外把藍牙的原始位址放在記憶體給「尋找」用，不顯示也不記錄。

## 已知限制

- 判斷靠追蹤器的藍牙位址。AirTag 與主人分開時大約每 24 小時才換一次位址，可以穩定追蹤。SmartTag 與 Google 的配件換位址的頻率較高，可能在達到門檻前就換掉，需要實測後調整
- 沒有 GPS，沒打開 Wi-Fi 移動判斷時，無法分辨「追蹤器跟著你移動」與「你待在追蹤器旁邊」。在家裡或辦公室待久了，鄰居的追蹤器也可能觸發警示，見下方「Wi-Fi 移動判斷」
- 與主人分開的 AirPods 也使用 Find My 的廣播格式，會被列入
- Tile、Chipolo、Pebblebee 自家的廣播不標示是否與主人分開，沒有同時發送 DULT 廣播的話，主人帶在身上的也會被列入
- 藍牙廣播沒有經過認證，任何裝置都可以假裝成某種追蹤器，或假裝主人在附近
- 識別規則參考公開的研究、AirGuard 專案、[Kismet 的追蹤器整理](https://www.kismetwireless.net/docs/readme/datasources/bluetooth-trackers/)與 DULT 規格草案，各型號都需要實際的追蹤器驗證。周圍還沒收到過 DULT 廣播，DULT 的判斷尚未實測

## 實測方式

`VERBOSE` 設成 `true` 時，每個符合特徵的廣播都會印出原始的廠商資料與 Service Data。拿社群成員自己的追蹤器測試：

1. 追蹤器放在板子旁邊，主人的手機關掉藍牙或帶離現場，確認 Apple 的廣播從 `12 02` 變成 `12 19`
2. 把門檻暫時調低（例如 `ALERT_MIN_SPAN_MS` 改成 2 分鐘），確認警示流程
3. 帶著板子與追蹤器走動，記錄各型號換位址的間隔
